Green Code: Play & Learn

Designing a level editor for a game that teaches programming.

ContributionUX & Game Design
StudioDreams Uncorporated
ScopeUX flows · mechanic design · prototyping · UX writing
PlatformsMobile, desktop and web

UI art and iconography were produced by a separate department. Published with the studio's permission.

Context

Green Code is a cross-platform app that teaches programming fundamentals through play, framed around environmental themes. Players solve challenges by chaining actions into a sequence of action blocks, by decomposing a task into smaller ones, or by finding an error in a block sequence.

I was brought in to test and improve the user experience design of a level editor, which came with the opportunity to fix some mechanics that the editor's logic broke.

The player becomes the author

An important insight I got while testing was that, until the editor, the player had to solve pre-designed challenges with static written instructions. Now, the same player who becomes a level creator has to make their own instructions and grids, and make sure the challenge is solvable for other players by solving it themselves first.

This called for a task to reverse-engineer the experience, where the design approach was finding the best way to give the player a usable and diverse level toolset — with all game attributes, hazards and action blocks — to create with.

Design decisions

After analysing the initial state of the editor with a user journey, a few decisions were made, prototyped, pitched and deployed:

  • An icon-based, categorised, collapsible inventory, which replaced a long scrollable list of more than a hundred items. Linear searching became efficient searching. This shipped for the action blocks; the hazard inventory iterated to a second solution and eventually shipped as a text-only dropdown.
  • A delete-whole-answer button, because clearing a long answer tile by tile punishes the experimentation an editor exists to encourage. This was implemented and adopted across the whole game.
  • Personalisation settings selected by the level creator — categorised by ecosystem, by difficulty (basic to advanced action blocks), by creative or realistic mode, and by algorithmic or decomposing — so players picked their tools beforehand, solving saturation from the start.
  • Grid pinpoints for the action requirement inventory, so the level creator could select and see where their required block actions sat on the grid instead of re-reading the generated instructions on every edit. This also let players solve the same created challenge with different answers, since the action requirements didn't call for a mandatory order.

Other proposals were set aside to get the editor shipped. They are still in the user flows. The art department made the final art and icons for the UI.

Game design tasks

Since the original levels had previously written instructions, we created a system where each required action block carries a phrase, and the blocks a level creator picks concatenate into the instruction the next player reads. I wrote that system so it would hold for any combination.

Redesigning a game mechanic

During development, the clients came with a new dilemma: an existing mechanic stopped making sense. The action block Plant had been designed for levels with fixed crops, and for the level editor the crops were replaced with one soil block and one water block. After reviewing the user journey and the as-is / to-be flows, I realised that the level creator had to learn how to use Plant all over again, without a context.

To ease that confusion I created a crop selection system, grouped by crop family, crop type and ecosystem, making sure the editor opened to every crop the player was already familiar with. After a few rounds with the client to settle which groups shipped, the first part was ready.

Making it fun

Harder levels needed to explore different challenges. Following the plant redesign, on medium and hard levels I added units per crop to the action requirements, to encourage level creators to use loops in their algorithmic levels and make them more challenging for other players.

Once those changes were in, I refined production's new scoring base for player-created levels into a system weighting answer match, length, response time, attempts and level difficulty. That score feeds a leaderboard where players see the global and regional top scores for the levels they solved, created by other players.

Finally, once everything in the level editor worked, I authored a set of levels made with the editor for a Recommended levels tab, so level creators learn the tool's range by playing rather than by reading.

Learning from the player, and helping the player learn

This project was a great way to explore how to give users as much freedom as possible and still keep the experience immersive and easy to use. I enjoyed working with the development team and the client to make it better and more memorable — I even had the opportunity to talk about our work live.

What I take from it is to always prioritise the user's mind and capability, keeping their intuition and knowledge on hand to tailor designs they not only need but also enjoy.
